This is a read-only design and correctness review of the `espnet3` package (and the `egs3/` recipes that drive it) at commit `ec5632b167`, which the local `upstream/master` also points at. Sixteen areas were each read in full by a dedicated reviewer; suspected bugs were reproduced with small scripts where feasible; then every critical, high and medium finding was re-checked by an independent verifier instructed to refute it. Of those 118 findings, 107 were confirmed as written, 10 were confirmed with corrections (severity or scope adjusted), and 1 was refuted and dropped. The 86 low-severity findings were not independently verified and rest on code reading.

Overall: the architecture is sound in its bones -- a staged pipeline on top of Lightning, cross-recipe dataset references via `data_src`, and a test suite that is mostly meaningful (711 tests, only 9 judged hollow or misdirected). But the review found a consistent set of system-design problems that produce most of the individual bugs, and they are cheapest to fix now, before the first release and while only two recipes exist. The single most important theme: the five per-recipe config files are used as a **shared, mutable message bus** between stages, and the pipeline is written as if one process runs every stage exactly once. Both assumptions break in the shipped multi-GPU and resume paths.

The highest-severity findings (all independently verified):

- **Silent wrong training (critical).** `collect_stats` destructively pops `model.normalize`/`normalize_conf` out of the shared training config, so running `--stages collect_stats train` in one process trains with the wrong (task-default) normalizer and saves a config that does not match what ran (`base-pipeline#01`). TTS has the mirror-image defect: it never strips normalize, so canonical `global_mvn` configs crash `collect_stats` (`tts-system#01`).
- **Silent stale statistics (critical).** `collect_stats` resume reuses per-shard outputs whose manifest fingerprints only the index plan, so after the dataset, preprocessor or model config changes the stage returns the old statistics without warning, and training then normalizes with stats computed for different data (`data-loading#02`). The same design flaw makes inference resume reuse old hypotheses after the checkpoint or beam size changes (`base-inference#02`).
- **No rank model under DDP (high).** Lightning's DDP launcher re-executes the entry point on every rank and `run_stages` has no rank guard, so every non-train stage (infer, measure, pack) runs N times against the same output directory and collides on locks (`base-inference#01`, `base-pipeline#12`). Distributed-ness is inferred from config values rather than the runtime, so one-GPU-per-node multi-node is treated as single-process (`data-loading#01`, `lightning-module#04`), and datasets can be sharded twice (`data-loading#03`).
- **Idempotency by directory existence (high).** Staleness is checked by file existence everywhere, writes are non-atomic, and shard locks are acquired eagerly and leak on failure, so interrupted runs poison later ones (`base-inference#03`, `egs3-recipes#01`, `data-organizer#04`, `asr-system#02/#03`, `parallel#01`).
- **Checkpoint averaging and EMA depend on Lightning's callback order, which Lightning changes (high).** `AverageCheckpointsCallback` averages the previous validation's top-K and never averages the final epoch; with EMA enabled the best checkpoints store online weights and no EMA state (`trainer-callbacks#01/#02`, `lightning-module#11`). Default callbacks are hard-wired and ordinary Lightning options crash at startup (`trainer-callbacks#03`).
- **The multi-optimizer path leaks gradients and mis-scales accumulation (high).** `manual_backward` deposits gradients into every reachable parameter and other optimizers' grads are not zeroed in time; `step_every_n_iters` sums N backward passes without scaling; accumulation state is discarded on resume and never flushed at epoch end (`lightning-module#01/#02/#05/#06`). The documented top-level `init:` is never applied (`lightning-module#03`).
- **The data layer conflates composition, mode flags, Hydra mechanics and sharding**, producing a cluster of collator/preprocessor/shape-file mismatches (`data-organizer#01/#02/#03`, `data-loading#07/#08`); several documented config keys are silently dead (`init`, `dataloader.*.total_shards`, `character_coverage`/`user_defined_symbols`, `create_dataset.func`); and the documented `measure` and `pack_demo` invocations crash on cross-file config references (`metrics#01`, `base-pipeline#03`).

Section 2b lays out the nine structural themes (A-I) behind these and the recommended direction for each; sections 3-4 give every finding with file, line, scenario and fix; section 5 is the triage punch list.

**Scope and caveats.** `espnet3/cli/` has no tracked Python source in this tree and was not reviewed. One originally-critical claim (that `python run.py --training_config conf/training.yaml` crashes because `__package__` is empty) was refuted by running the command and is listed in appendix 6.3. Every finding of every severity, including that one, is preserved in `review_log/all_findings.json` and as a fix checklist in `review_log/BACKLOG.md`. Findings are pinned to `ec5632b167`; the maintainer has a separate data-layer bugfix branch that may already address some `data-organizer`/`data-loading` items -- after fetching newer `upstream/master`, `python3 review_log/tools/recheck_after_merge.py upstream/master` lists which findings touch changed code.
