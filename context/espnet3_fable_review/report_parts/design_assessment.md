The individual findings cluster into a small number of system-level design problems. Fixing the bugs one by one without addressing these will keep producing the same class of defect. Finding ids in parentheses refer to section 3 / `review_log/BACKLOG.md`.

**A. Shared mutable `DictConfig` objects are the inter-stage bus.** `run.py` loads five YAML files once and every stage reads and *writes* those same objects: `collect_stats` pops `model.normalize` (base-pipeline#01, critical), `infer` sets `config.test_set` and `parallel.options` in place (base-inference#15), `set_parallel(None)` inherits a previous stage's cluster config (parallel#04), and the cross-file references (`exp_dir`, `inference_dir`, `exp_tag`) are bridged by ad-hoc key copying in `apply_training_experiment_context`, which is why the documented `measure` and `pack_demo` invocations crash when a file is loaded on its own (metrics#01, base-pipeline#02/#03). There is no explicit experiment-context object and no notion of a stage *returning* artifacts. Recommendation: derive one immutable, fully resolved `ExperimentContext` (recipe_dir, exp_dir, stats_dir, tokenizer paths, inference_dir) once; hand each stage a read-only copy of its config plus the context; stages produce artifacts on disk and return their paths instead of editing the config another stage will read.

**B. The orchestrator is split across five files, one of them inside a recipe.** Stage dispatch lives in `systems/base/system.py`, `systems/base/training.py`, `utils/stages_utils.py`, `utils/run_utils.py` and `egs3/TEMPLATE/asr/run.py`, and the real recipes import the last one (`from egs3.TEMPLATE.asr.run import main`). Library logic (argument parsing, the required-config guardrail, context application) therefore lives under `egs3/`, and `default_package=__package__` couples config defaults to the Python package of whichever script is executing, which is what breaks the documented `python run.py ...` invocation (config-hydra#01). `espnet3/utils/` is 3.7k lines and holds core subsystems (`run_utils.py` 554, `publication_utils.py` 749, `logging_utils.py` 996) plus dead code (`download_utils.py`, misc-utils#05). Recommendation: an `espnet3/runner` (or the empty `espnet3/cli`) package that owns the entry point (`python -m espnet3 run --recipe ...`), stage registry and context; recipes keep only `conf/` and `src/`. Move `publication_utils.py` into `publication/`, `collect_stats.py` out of `components/data/` (it is a stage), and dissolve `utils/` into named subpackages.

**C. There is no process/rank model.** The pipeline is written as if one process runs all stages, but Lightning's DDP launcher re-executes the entry point on every rank, so every non-train stage runs N times against the same output directories (base-inference#01, base-pipeline#12). Distributed-ness is inferred from the *config* (`num_device > 1`, `dist_world_size`) rather than from the runtime, so multi-node with one GPU per node is treated as single-process (data-loading#01, lightning-module#04) and datasets can be sharded twice (data-loading#03). Recommendation: a `DistContext` (rank, world_size, is_main) derived from `torch.distributed`/environment at process start; each stage declares whether it runs on the main rank only or on all ranks and `run_stages` enforces it; launch `train` separately from the single-process stages.

**D. Idempotency and resume are implemented by directory existence.** `is_built`, `is_source_prepared`, `_has_tokenizer` and the stats/tokenizer checks test only that files exist; runner manifests fingerprint the shard plan but not the model or config, so a changed checkpoint or beam size silently reuses old outputs (base-inference#02, data-loading#02); writes are not atomic (egs3-recipes#01, data-organizer#04, asr-system#02/#03); locks are acquired eagerly and never released on failure (base-inference#03, parallel#01). Recommendation: one small artifact helper used by every stage and every recipe builder: write to a temp path and rename, write a `.done` sidecar carrying a fingerprint of the inputs and relevant config, and a lock helper with `try/finally` release.

**E. The dataset layer tangles composition, mode flags, Hydra mechanics and sharding.** `DataOrganizer` only works when the user's YAML carries `_recursive_: false` (data-organizer#20) and behaves differently when `_convert_: all` turns a `DictConfig` into a dict (base-inference#04). `CombinedDataset` has two item protocols (`dict` vs `(uid, sample)`) selected by a flag that the LightningModule sets from outside and that `shard()` forgets (data-organizer#01), while `collect_stats` keys its decision on a *different* flag (data-organizer#02). Shape files are keyed by global integer indices that shift whenever the composition changes (data-loading#08), sharding is incompatible with the iter-factory path (data-loading#07), and `data_src` resolution builds synthetic modules whose classes cannot be pickled by spawn-based workers (data-organizer#09). Recommendation: let `DataOrganizer` own composition and preprocessing only, instantiate its nested configs itself (so YAML does not need Hydra flags), and expose a single item protocol with a stable per-utterance uid supplied by the sub-dataset; move sharding and iteration entirely into the DataModule.

**F. The parallel Runner/Provider abstraction leaks.** Runner bookkeeping keys and provider parameters share one flat `**env` namespace (parallel#02); "do not capture self" is violated by the framework's own providers so whole datasets are pickled to workers (parallel#06, and the 5 MB payload in the duplicate provider); a Dask cluster is created and torn down per runner call (parallel#03); two different `InferenceProvider` classes share a name (base-inference#13); `env: local` silently ignores `n_workers` (base-inference#09); constructor arguments are dead (parallel#07). Recommendation: a typed `RunnerContext` separate from provider params, cluster lifetime owned by the stage (context manager), delete the duplicate provider, and either honour `n_workers` locally or reject it.

**G. Trainer composition is hard-wired and correctness depends on callback order.** Default callbacks cannot be disabled or replaced (trainer-callbacks#03), and checkpoint averaging and EMA-checkpoint consistency rely on Lightning's callback ordering, which Lightning changes by moving `ModelCheckpoint` to the end (trainer-callbacks#01/#02, lightning-module#11). Recommendation: make defaults opt-out and coordinate averaging/EMA through explicit checkpoint hooks rather than adjacent callbacks.

**H. `asr` and `tts` diverge because the base class is thin.** `BaseSystem` is mostly stubs, so each system re-implements stage plumbing and they disagree on the constructor contract (tts-system#04), on `model.normalize` handling (opposite behaviour, tts-system#01 vs base-pipeline#01), on `stats_dir` conventions (tts-system#12), and TTS-specific stages are in no stage list and their outputs are consumed by nothing (tts-system#06/#14). Recommendation: move directory conventions, config access, staleness checks and logging into the base and let systems supply hooks only.

**I. The config surface is large and unvalidated.** Five YAML files per recipe repeat the same path scaffold; `exp_tag` is derived from the config *filename* (`self_name`); and several documented keys are dead: `create_dataset.func` (egs3-recipes#02), `dataloader.*.total_shards`/`dist_world_size` (data-loading#04), `tokenizer.character_coverage`/`user_defined_symbols` (asr-system#01), top-level `init` (lightning-module#03). Recommendation: structured configs (dataclasses) validated at load time so unknown or dead keys fail fast, and a shared common section instead of five copies of the path scaffold.

What is structurally sound: the staged-pipeline idea itself, the decision to build on Lightning, cross-recipe dataset references via `data_src`, and the test suite, which is largely meaningful (711 tests, 9 judged hollow or misdirected).
