# asr-system findings notes (incremental)

## espnet3/systems/asr/system.py
- L174-180: `train_tokenizer()` calls `train_sentencepiece(train_text_path, output_path, vocab_size, model_type=...)` and never forwards `tokenizer_config.character_coverage` or `tokenizer_config.user_defined_symbols`, even though every real recipe config in this area declares `tokenizer.character_coverage` and `train_sentencepiece()` accepts both params. Currently invisible because all checked-in configs set `character_coverage: 1.0` (== the function default), but changing it in a YAML (e.g. to 0.995 for CJK-style coverage, a documented espnet2 convention) has zero effect. Confirmed by reading; test `test_asr_system_train_tokenizer_trains_sentencepiece`'s fake mirrors only the 4 args actually passed, so the gap is untested. Severity: high (silent, realistic-config divergence).
- L94-99 `_has_tokenizer()` + L113-180 `train_tokenizer()`: "already trained" is defined as "`{model_type}.model` and `{model_type}.vocab` exist at save_path" only.
  1. Incompleteness: `tokens.txt` is written *after* those two files (sentencepiece.py L148-161, via `shutil.move` then a separate `open(...).write`). If the process is killed/preempted between the vocab move and the tokens.txt write (plausible on a Slurm/HPC cluster - this repo's own working tree lives under `/work/hdd/...`), `_has_tokenizer()` returns True on retry and `train_tokenizer()` is skipped, but `${tokenizer.save_path}/tokens.txt` (referenced by `model.token_list` in every config) is missing, so the *next* stage fails, and the only fix is to manually delete the model/vocab files.
  2. Staleness: nothing hashes the tokenizer's input text or `text_builder`/`character_coverage`/`user_defined_symbols` config. `save_path` is only parameterized by `${tokenizer.model_type}_${tokenizer.vocab_size}` in the shipped configs, so re-running `create_dataset`/train after fixing a transcript-normalization bug (manifest content changes) or changing `character_coverage`/`user_defined_symbols` silently reuses the old tokenizer artifacts with no warning. Matches task brief's explicit ask about staleness detection. Severity: high (silent wrong-result risk in a realistic iterative-dev workflow, not just first-run).
- L162-165: if `train_text_path` already exists, `train_tokenizer()` unconditionally raises `RuntimeError` ("Tokenizer training text already exists"). Combined with the two points above: if a prior run wrote `train.txt` and then crashed before/during `train_sentencepiece`, `_has_tokenizer()` is False on retry (no model/vocab yet) so `train_tokenizer()` runs again, immediately hits this guard and raises - the stage can never recover on its own after a partial failure; the user must know to delete `data_dir/train_tokenizer/train.txt` by hand. Explicitly a non-idempotency bug in a staged/resumable pipeline. Severity: high. (Test `test_asr_system_train_tokenizer_rejects_existing_train_text_path` only checks the guard fires; it doesn't flag that this makes the stage non-resumable.)
- L174: leftover `# Example placeholder:` comment directly above the real `train_sentencepiece(...)` call - looks like an unfinished stub comment shipped in production code (cosmetic/misleading, low severity).

## espnet3/systems/asr/tokenizers/sentencepiece.py
- L196-224 `add_special_tokens`: the `for token in add_token_list: ... m.pieces.insert(insert_position, p)` loop reuses the same `insert_position` for every token instead of incrementing it, so when 2+ special tokens are added they land in the underlying `ModelProto.pieces` list in **reverse** order relative to `new_converter.token_list`/`new_embedding` (which are built correctly, in forward order, via list-slicing). Verified by execution (repo script): with `add_special_tokens(..., ["<intent>", "<speaker>"], insert_after="<unk>")`, the returned `new_converter.token_list` reads `[..., "<intent>", "<speaker>", ...]` but the raw model file loaded back with `spm.SentencePieceProcessor` shows piece id order `[..., "<speaker>", "<intent>", ...]`. Because `TokenIDConverter`/`SentencepiecesTokenizer` resolve ids purely by piece *string* (see `espnet2/text/token_id_converter.py` L33-36, a plain string->index dict built from the passed `token_list`), the returned `(new_tokenizer, new_converter, new_embedding)` triple stays internally self-consistent for training, so this is not shown to break the tested/returned objects directly. It does corrupt the *persisted* `_sp.model` file's own internal vocabulary order, which silently breaks correctness for any downstream consumer that reconstructs a token list from that model file's own piece order (e.g. the same pattern `train_sentencepiece()` itself uses when deriving `tokens.txt` from a `.vocab` dump) instead of reusing the returned `new_converter`. No test exercises the 2-tokens-with-insert_after case against the raw model's own ordering (existing test only checks `new_converter.token_list`, not `sp.id_to_piece()`). Severity: medium (real, verified bug; narrower blast radius than a training-time corruption). `verified_by_execution: true`.
- No validation that `vocab_size` (and `character_coverage`) leave enough room for the corpus's required character set before calling into `spm.SentencePieceTrainer.Train`. Verified by execution: `train_sentencepiece(text, dir, vocab_size=20, model_type="unigram")` on a ~20-unique-character toy corpus raises `RuntimeError: Internal: ... Vocabulary size is smaller than required_chars. 20 vs 21. Increase vocab_size or decrease character_coverage...` - a raw C++ SentencePiece error with no espnet3-level guidance, propagating straight out of `ASRSystem.train_tokenizer()`. The same failure class applies to `model_type: bpe` (all three shipped configs use bpe with `vocab_size: 30`, a tight, undocumented margin over AN4's character set) not just unigram. Severity: medium (currently passes CI, but fragile/cryptic failure mode for any future text or vocab_size edit; matches the salvage-log lead on unigram feasibility, generalized to bpe too). `verified_by_execution: true`.
- L17-81 `prepare_sentences`: has zero callers anywhere in `espnet3/`/`egs3/` outside its own tests (train_tokenizer's real text builders in `egs3/mini_an4` and `egs3/librispeech_100` don't use it) - dead production code. Also `line.split(" ", maxsplit=1)[1]` (L77) will raise an undocumented `IndexError` for any input line without a space (e.g. a blank-transcript utterance id with no text), which isn't listed in the docstring's `Raises` section. Severity: low (unused code path).
- L90 `train_sentencepiece(..., user_defined_symbols: list = [])`: mutable default argument anti-pattern; currently harmless since the list is only read, never mutated, but a latent landmine. Severity: low.

## espnet3/systems/asr/transducer_task.py
- L421-426: `ASRTransducerTask.build_model` unconditionally does `if args.init is not None: raise NotImplementedError(...)`, yet `add_task_arguments` (L118-123) defines `--init` as a normal, freely-settable string option with no indication in help text that any non-None value is fatal. `training_asr_transformer.yaml` and `training_asr_transducer.yaml` in the same directory (both routed through `espnet3.systems.asr.task.ASRTask`, which *does* support `init`) both set `init: xavier_uniform` - an easy trap for anyone adapting that same pattern into an `ASRTransducerTask`-based recipe (`task: espnet3.systems.asr.transducer_task.ASRTransducerTask`, e.g. `training_transducer_asr_conformer_rnnt.yaml`, which currently avoids the crash only by omitting `init:` entirely). `test_asr_transducer.py::test_build_model`'s dummy namespace always uses `init=None`, so this branch is completely untested. Severity: medium (config-vs-code divergence / latent trap + test-gap; not reachable via the currently checked-in transducer_task config).
- Deps check (context, not a new finding): `training_transducer_asr_conformer_rnnt.yaml` *is* wired into `ci/test_integration_espnet3.sh` (L70) and its default loss path lazily imports `warprnnt_pytorch` (`espnet2/asr_transducer/espnet_transducer_model.py` L404, calling `exit(1)` on `ImportError` if missing - an abrupt, non-Pythonic failure mode, but pure espnet2 code). Confirmed `ci/install.sh` L38-40 does install `warp-transducer.done` as part of the real CI `make` target list, so this path is exercised successfully in CI; only this local review sandbox lacks the compiled extension. Not filing as a bug (checked and OK for CI); worth noting `exit(1)` (vs raising) would still be unfriendly for anyone using `pip install espnet[...]` without the Makefile installers.

## Tests (test_system.py, test_task.py, test_asr_transducer.py, tokenizer/test_sentencepiece.py)
- Tokenizer tests are solid for the paths they exercise (happy path, missing builder func, non-existent builder output path, invalid builder return type, empty text, pre-existing train_text_path, already-trained skip) but mirror the current `train_sentencepiece` call signature (4 positional/keyword args) rather than asserting `character_coverage`/`user_defined_symbols` forwarding - the coverage gap above is invisible to this suite by construction.
- No test re-runs `train_tokenizer()` a second time against changed input text/config to check for staleness, and no test simulates a crash between writing `train.txt` and completing `train_sentencepiece` to check resumability.
- `test_sentencepiece.py::test_train_sentencepiece_and_add_special_tokens` only ever adds tokens with `insert_after` set to a target already at/near the end of its own sub-list issue window (single index check `new_converter.token_list[insert_at:insert_at+2]`) and never inspects `sp.id_to_piece()` on the modified raw model, so the reversed-insertion-order bug above has no coverage.
- `test_asr_transducer.py` never exercises `args.init is not None` for `ASRTransducerTask.build_model`.
