## test/espnet3/components/data/test_collect_stats.py -- CONFIRMED BUG (verified_by_execution)
`DummyDataset.__getitem__` (L52-78) returns `(uid, sample)` tuples gated directly on its own `use_espnet_preprocessor` constructor arg. But the real `CombinedDataset.__getitem__` (espnet3/components/data/dataset.py L181-213) gates the `(uid, sample)` tuple return on `use_espnet_collator`, a SEPARATE flag that `collect_stats.py`'s `build_env_local`/`build_worker_setup_fn` (L246-247, L271-272) set to `isinstance(collate_fn, CommonCollateFn)` -- i.e. it becomes False whenever a custom (non-CommonCollateFn) collate_fn is configured. `collect_stats_batch` (L43-51) branches on `use_espnet_preprocessor` (not `use_espnet_collator`) to decide whether `dataset[i]` is a tuple. Verified with a real `CombinedDataset(use_espnet_preprocessor=True)` + `use_espnet_collator=False` (the real state whenever a custom collate_fn is configured for an ESPnet-preprocessed dataset): `dataset[i]` returns a bare dict `{"speech":..., "text":...}`, and `uid, sample = item` in collect_stats_batch silently unpacks the dict's own KEY NAMES as strings (uid="speech", sample="text") with NO exception raised -- confirmed by running the real functions (script: repro_collect_stats.py). Every custom-collate_fn + use_espnet_preprocessor=True recipe silently gets garbage uids/features out of collect_stats (or a ValueError if the sample dict doesn't have exactly 2 keys), and none of test_collect_stats.py's `use_parallel`/`use_espnet_preprocessor` x `DummyCollate` parametrizations can ever catch it because DummyDataset's contract is wired to match the (wrong) assumption instead of the real CombinedDataset contract.
